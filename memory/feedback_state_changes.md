---
name: 状态变更操作前必须征求确认
description: 改变项目/系统状态的操作（push、rebase、删文件、装依赖等）执行前要先问用户
type: feedback
---

涉及改变项目/系统状态的操作，**做之前要先告知并等用户同意**，不能自行执行。代码改动（编辑文件、新建文件）可以直接做。

**Why:** 用户希望对状态变更保留控制权——状态变更难撤销、可能污染他配置/远端、可能让他丢上下文。代码改动是本地、可逆、低风险，不需要打断流程。这条规则在 2026-04-28 由用户明确提出。

**需要先确认的具体操作类别**（用户明示）：
- `git push`、`git rebase`、`git reset --hard`、`git branch -D` 等远端/破坏性 git
- 删除文件（任何 `rm`/`Remove-Item`/`Delete`）
- 改环境变量（系统级或用户 profile，不是单条命令的 inline env）
- 安装/卸载系统依赖（`winget install`、`choco install`、`apt`、`apk` 等）
- 改 docker daemon 配置、systemd unit、防火墙规则等基础设施

**不需要确认的**：编辑/新建项目内文件、跑测试、跑 build、`go mod tidy`、`npm install`（项目内 node_modules）、临时启停**自己启的**进程。

**How to apply:**
- 想做上面任一类操作时，先写一句"我打算 X，因为 Y，可以吗？"等用户回复
- 提议时附上回滚方法（"如果有问题可以 `git reflog` 找回")
- 如果用户在指令里**明确授权**了某操作（"你 push 一下"），那次直接做即可，但授权范围仅限那次

## 事后必须立刻汇报状态（2026-04-28 用户补充）

授权后做完状态变更，**立刻**用结构化格式汇报当前实际状态，不要混在长说明里。Phase 2.1→2.2 之间 Junction 失败那次就是这个范本，用户认可：

```
| 项 | 状态 |
|---|---|
| <被删/改的资源1> | 已删除 / 已修改 |
| <新创建的资源2> | 已创建 / 路径 X |
| <未动的资源3> | 完好未动 |
```

要求：
- 列出**所有**被改动的具体路径/资源，不要笼统说"做完了"
- 列出**所有**没动的相关资源（特别是用户可能担心被波及的），让用户确认不需要排查
- 失败状态也要列：哪一步成功了、哪一步失败了、失败前的清理状态
- 这一段在响应里**单独成块**，不混在解释里
