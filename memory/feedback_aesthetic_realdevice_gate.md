## 教训

审美/动效类 release 的"成功"不能只看 CI 绿. CI / release.yml 全绿只证明
"代码不报错 + 镜像能 build", 不证明"好看". 动效气质 / alpha / 节奏 / 是否
自然 — 只有真机 + 用户眼睛能定稿.

## 活案例: v0.2.25 → v0.2.26 → v0.2.27 三轮迭代

- **v0.2.25** (整屏呼吸 + 光晕): CI 全绿, 真机 ship 成功, 但 Bevan 真机看
  "圈圈放大不自然 + 大范围呼吸不适" → **审美失败, 上线即返工**.
  ★ CI 绿 ≠ 好看 的活生生反面案例 ★
- **v0.2.26** (星空粒子): 流星"非常棒", 但星星"像定在原位" → 部分对
- **v0.2.27** (此起彼伏 8s + 对比拉大): Bevan "效果非常不错, 我喜欢" → 定稿

3 个 release 跨 2 天 ship, 全部 CI 绿, 但只有 v0.2.27 真机满意.

## 关键失误: mockup 骗了我们

- mockup 用小框 (380px) + 无壁纸预览, 看不出全屏 + 叠真实壁纸的问题
- v0.2.25 的"圈圈放大"在小框 mockup 看不出, 全屏真机才暴露
- ★ mockup 是"逼近", 真机才是"定稿" ★

## 行动准则

1. 审美 release 的视觉门 = 真机 + 用户判断, **不是 CI 绿**
2. mockup 只用于"方向对不对", 不用于"参数定稿"
3. 本地 dev 缺 backend / 壁纸时, 直接 ship 真机当视觉门 (接受 1-N patch 迭代)
4. 审美 patch (alpha / 节奏 / 密度) 是审美 release 的**固有成本**, 非工程纪律失败
5. 参数靠真机迭代 (v0.2.25 → 27 三轮), 不指望一次 ship 到位

## How to apply

收到审美/动效类 spec 时:
- 不承诺"一次到位", 主动 surface "真机门必有 1-N 轮微调"
- 不把 CI 绿当 ship 完成度的最终标志
- mockup 提案附带"真机可能调参数"的预期管理
- 跟 [[feedback_visual_gate_iter_healthy]] 配合 — 健康范围 1-5 patches
